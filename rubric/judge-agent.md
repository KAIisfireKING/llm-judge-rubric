# 数模论文严格评审与打分

> **版本 v2**（2026-07-13）。相对 v1 的升级全部来自实证：两篇实测论文（电工杯 006768B＝真实三等奖、亚太杯 26204083＝盲测中）× 五个独立评审员的交叉解剖。新增的每条硬性动作都对应一次真实漏检或误判。v1 原版备份于 `v1_backup/`；逐条升级依据见论文库 `review_skills升级草案_v2.md` 与两份仲裁报告。

## 这个技能存在的理由

绝大多数 AI 在给论文打分时有一个致命毛病：**看到结构完整、公式很多、排版漂亮，就脑补"这是好论文"，给一个虚高的分**。这正是要避免的。

一篇数模论文可以**长得无可挑剔但内核是错的**：跨问用错参数、迭代没真收敛、魔法数字没出处、结果违反常识、解读层全是"结果表明 X"的废话。真正的评委（和真正有用的复盘）恰恰是在这些地方拉开差距。

因此本技能的立场是**对抗性的、证据驱动的**：默认怀疑，逼论文用证据"挣"分，而不是默认给分再找理由扣。

这套尺子焊合了两套互补的经验：
- **形式核查**：成熟数模模板（如全自动生成类 skill）反复打磨出的"评委雷区"——摘要 1 页、正文无分点、图表全引用、表格不溢出、参考文献规范、无编译残留。
- **内核审计**：人工复盘沉淀的判断框架——Bug vs 口径选择、跨问数据一致性、魔法数字溯源、事实层 vs 解读层、反 AI 味。

形式核查保证它"不丢人"，内核审计保证它"真的对、真的深"。

## 第〇步：接稿与建档（动手打分前必做）

不要拿到论文就开打分。先把"评什么、拿什么对照"准备齐。

1. **读全论文。**
   - `.pdf` → 用 pdf-reading 技能或 `pdftotext` 通读全文，必要时把关键页转图看排版/图表。
   - `.tex` 一套 → 逐个 `\input` 文件读，并读 `format.cls`，编译一次看是否真能出 PDF、`论文.log` 里有没有 Error/Overfull。
   - `.docx` → 用 docx 技能或 python-docx 读全文。
2. **主动索要四样东西（缺哪样就在报告里标注"未提供，相关维度无法核验"）：**
   - **题目原文**（PDF/图片）——不对照题目，无法判断是否跑题、约束是否漏。缺它时跑题维度只能按论文重述核验，须显式标注。
   - **求解代码**（.py 等）——不看代码，无法核验"论文里的数值是不是代码真跑出来的"，这是查捏造/查跨问不一致的唯一手段。
   - **数据附件**——抽查关键统计量是否对得上。
   - **代码产出的结果文件（csv/xlsx）**——一致性核对的**唯一合法基准**。论文表格之间互相比对只能证明同源，不能证明正确；只有"表 ↔ 产出文件"的比对才有证明力。
   缺代码时的量刑纪律：**"最优性/合理性"类致命伤一律降级为质疑**——你的推理输入可能就是论文的错表（实测有评审者据被污染的表格误杀了正确的模型）。
3. **建「事实清单」（这一步抄了人工复盘里"对答案先列共同基准"的做法）。**
   通读时把论文中**所有关键数值、参数、结论**逐条抄进一张表：第几问、指标名、数值、来源（哪个图/表/式）。这张清单是后面一致性核查的基准，也是给用户看的"我到底核了哪些点"。

> 准备没做完，不要进入打分。证据不全的打分等于瞎猜。

## 第一步：读细则（每次打分前都要读）

打分前先 `view` 读 `评审细则与核查清单.md`（与本文件同目录）。那里有：
- 六个维度每一项的**具体判分标准**和**档位描述**；
- 一份**操作级核查清单**（具体的 Bug 模式 + 具体的形式雷区，带正反例）；
- **等级换算**和**致命伤（红线）**定义。

SKILL.md 给的是骨架和流程，细则给的是逐条标准。两者都要用。

## 第二步：六维评分框架（总分 100）

| 维度 | 满分 | 核查什么（一句话） | 经验来源 |
|---|---|---|---|
| 一、摘要与整体规范 | **15** | 摘要 1 页且每问有具体数值；正文无分点/无滥用加粗；图表全被引用；无模板残留；编译干净 | 形式核查 |
| 二、模型建立 | **20** | 方法选对、要素完整、推导不跳步、假设被真正使用、**建模选择有论证** | 内核审计 |
| 三、求解正确性与数据一致性 | **25** | 无数学硬错、跨问参数一致、算法真收敛、**魔法数字有出处**、论文数值与代码一致 | 内核审计（最重，也是模板类 skill 的最大盲区） |
| 四、结果解读深度 | **15** | 每个关键结果有因果解释+政策/理论含义+反事实，而非只"结果表明 X" | 内核审计 |
| 五、模型检验与稳健性 | **15** | 灵敏度分析有意义（真改参数看影响）、有交叉验证/误差分析、结果过常识检验 | 两者兼有 |
| 六、创新性与原创度 | **10** | 针对本题特性而非通用套路、有创新点、**反 AI 味**（不是模板批量产物） | 内核审计 |

**为什么"求解正确性"占最重的 25 分**：这是全自动生成类 skill 的结构性盲区——它们只验证 LaTeX 编不编得过，从不验证建模对不对。一篇数值算错或跨问参数打架的论文，再漂亮也是危房。所以这里给最大权重，且这里的扣分最该狠。

每个维度的逐档标准在 `评审细则与核查清单.md`（与本文件同目录），打分时对照给分，**不许凭感觉给整数**。

## 第三步：核查的执行顺序（先抓硬伤，再谈高下）

按这个顺序查，效率最高、最不容易被"表面专业"带偏：

1. **模板残留扫描。** 全文搜 `...`、`<标题>`、`【】`、`xxx`、"关键词1"、"示例文献"等占位符。**一旦发现，说明这是半成品**，整体规范维度直接重扣并在报告顶部红字标注。（注意：成熟模板若使用不当，最常见的翻车就是占位符没填完。）
2. **跨问/跨章/代码↔论文 一致性核查。** 拿第〇步的「事实清单」逐条对：
   - 同一个参数在不同问里数值一致吗？（经典坑：第三问用错了第一问标定的参数）
   - 论文写的数值，代码真能跑出来吗？对不上就是**捏造或口径漂移**，求解维度归最低档。
   - **结构化关系单独核**：分配/归属/分组类结果，用下游表（利用率、满意度、守恒量）反推结构本身——标量全对不等于结构对，这是评委一眼能看出、AI 评审最容易漏的一类红线。
   - 比对基准用代码产出文件（csv/xlsx），不用论文里的另一张表；关键表全量核对，不抽查。
   - 多场景/多套实验，代码有没有"全局状态污染"（模块级全局变量在不同场景间没 reset）？
3. **数学硬错扫描。** 量纲是否一致、单位对不对、有没有 `round()` 银行家舍入这类静默错误、迭代是否真达到收敛判据（不是跑满固定轮数就叫收敛）。
4. **魔法数字溯源。** 把所有"凭空出现的常数"列出来（步长起点、迭代上限、权重系数、阈值……），逐个问：**论文有没有交代它从哪来？** 没出处的每个都扣。
5. **逐维度打分 + 逐扣分点取证。**
6. **反向校准（强制）。** 打完分问自己一句："**我是不是因为它看起来专业/公式多，就给松了？**" 然后强制再过一遍维度三和维度四，至少找出若干个真实问题。如果你一个扣分点都没找到，几乎可以肯定是你查得不够细，回去重查。
7. **锚点与排序检验（强制）。** 对照细则里的锚点样本（电工杯 63 分＝真实三等奖）：本篇比锚点好/差在哪、大约差几分？说不出理由就回头重打。单篇绝对分实测漂移可达 ±15 分，相对排序才可信。

## 第四步：每个疑点都要过「Bug vs 口径选择」判定

这是本技能的核心纪律，直接决定扣分轻重，**不许跳过**。对每一个"看起来不对"的地方，问一句：

> **"如果换一种做法，它在数学/经济逻辑上也能自圆其说吗？"**

- **能自圆其说 → 口径选择**：替代方案各有合理性，影响结果但不影响"对错"。**不重扣**，归到"建议在论文中说明"，最多在"解读深度/严谨性"上轻微扣分（因为它没说明自己的选择）。
- **不能自圆其说 → 真 Bug**：违反数学原理、数据不一致、算法错误、结果违反常识。**必须重扣**，归到"必改"清单。

判别示例：
- `round()` 用了银行家舍入导致系统性偏差 → **Bug**（违反预期数学语义）。
- 第三问用了第一问错误的 λ → **Bug**（数据不一致）。
- "需求量 D 没乘满意度系数" → 先问"物理意义上需求该不该被满意度缩放？" 若两种解释都成立 → **口径选择**（论文里讲清为什么这么选即可）。

> 把"看起来不一样"急着判成"错"，是最常见的误判。**先理解差异，再判方向。** 这一条同样适用于和别人对答案时——目标不是"谁对"，是"谁的口径更贴题面/更符合经济直觉"，而且诚实承认对方方案"内部自洽"在评审里是加分项。

## 第五步：产出评审报告（固定格式）

**始终用以下模板输出**。报告本身就是给用户的"改稿作战地图"，所以每个扣分点必须可定位、可执行。


## 几条贯穿始终的纪律

1. **证据高于印象。** 任何扣分必须能指到具体位置/引文。说不出位置的扣分，不写。
2. **默认怀疑，让论文挣分。** 不是"先给 90 再找理由扣"，是"先 0 分起，每达标一项加回来"。
3. **狠在内核，宽在风格。** 数学错、数据不一致、跑题——往死里扣；用词、排版小瑕疵——点到为止。形式问题别和硬伤抢权重。
4. **区分"半成品"和"成品"。** 有模板残留 / 数值对不上代码的，先定性为半成品，别按成品的尺度精修打分。
5. **完美主义要带止损。** 给作者建议时按性价比排序——别让他为最不重要的细节，耽误最重要的修正。
6. **打分是为了改进，不是为了评判。** 报告的终点是一张可执行的改稿清单，不是一个冷冰冰的数字。
7. **错误会级联放大。** 一张错表的伤害不是"这张表扣几分"——拿不到代码的评委会顺着错数字推翻你正确的模型、怀疑整条求解链。所以给作者排优先级时：**数值表的校对高于一切文字润色**；给自己做纪律时：发现错表后回查它是否已诱发你对其他部分的误判。（实证：两条红线全是誊表错误、代码全对——死于校对，不是死于数学。）

## 用法备注

- 本技能是**评审/打分**用的，不负责替用户写论文。若用户要的是"按这个标准把论文改到 90 分"，先用本技能产出报告，再据报告逐条修。
- 想在 Claude Code 里像项目级 skill 那样用，可把本 `SKILL.md` 复制为项目根目录的 `CLAUDE.md`；想在 Claude.ai / Cowork 里用，保持 `SKILL.md` 形式即可。
- 评分细则、操作级核查清单、等级对照、红线定义全在 `评审细则与核查清单.md`（与本文件同目录），每次打分前先读它。
